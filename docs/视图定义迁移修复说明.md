# 视图定义迁移修复说明（v2.3.2）

> 本文档说明 v2.3.2 版本对「视图→视图」定义迁移模式的四项修复，解决用户反馈的「关系已经存在」与「关系不存在」两类错误。

## 一、问题背景

用户执行视图定义迁移任务（`view_migration_mode = 'definition'`）时遇到两个错误：

```
[ERROR] 创建视图失败: 错误:  关系 "efmis_ksd_2010ys_aa" 已经存在
[ERROR] 创建视图失败: 错误:  关系 "acct_t_vchrno" 不存在
```

### 1.1 错误一：目标对象已存在但未被检测到

**根因**：存在性检查使用 `information_schema.tables` 视图，该视图内置权限过滤（`pg_has_role` / `has_table_privilege`），当 PG 用户对目标对象无显式权限时会**漏检**，导致 `CREATE VIEW` 时才报「已经存在」。

**影响**：之前物化模式（`materialize`）创建的表残留，定义模式无法检测到，导致 `CREATE VIEW` 失败。

### 1.2 错误二：视图依赖的基表未迁移

**根因**：Oracle 视图 SQL 引用的基表（如 `acct_t_vchrno`）尚未迁移到目标 schema，`CREATE VIEW` 执行时 PG 找不到基表。

**影响**：视图创建失败，但此前无前置预警，用户需在 CREATE VIEW 失败后才能知道缺哪些基表。

### 1.3 error 策略中断整批迁移

**根因**：冲突策略为 `error` 时，第一个已存在对象会触发 `raise Exception`，导致整个多视图任务立即终止，后续视图无法继续。

## 二、修复内容

### 2.1 存在性检查改用 pg_class（核心修复）

**修改文件**：[migration_app/views.py](../migration_app/views.py) `_migrate_view_definition` 函数

**修改前**：
```python
# information_schema.tables 有权限过滤，可能漏检
SELECT table_type FROM information_schema.tables
WHERE table_schema = %s AND table_name = %s
```

**修改后**：
```python
# pg_class 无权限过滤，可检测 schema 下所有关系
SELECT c.relkind FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = %s AND c.relname = %s
```

`pg_class.relkind` 支持的对象类型映射：

| relkind | 类型 | DROP 语句 |
|---------|------|-----------|
| `r` | BASE TABLE（普通表） | `DROP TABLE` |
| `v` | VIEW（视图） | `DROP VIEW` |
| `m` | MATERIALIZED VIEW（物化视图） | `DROP MATERIALIZED VIEW` |
| `S` | SEQUENCE（序列） | `DROP SEQUENCE` |
| `f` | FOREIGN TABLE（外部表） | `DROP TABLE` |
| `p` | PARTITIONED TABLE（分区表） | `DROP TABLE` |

### 2.2 error 策略改为 continue（防中断）

**修改前**：
```python
if strategy == 'error':
    raise Exception(f"目标对象 {target_schema}.{target_view} 已存在（{obj_type}）")
```

**修改后**：
```python
if strategy == 'error':
    make_error_log(log, f'目标对象 {target_schema}.{target_view} 已存在（{obj_type}）')
    failed.append(view_name)
    continue  # 记录失败并跳过，不中断整批迁移
```

**效果**：多视图迁移中单个已存在对象不再中断后续视图，任务最终状态为 `partial`（部分失败）。

### 2.3 replace 策略 DROP 安全兜底

**新增逻辑**：即使 `pg_class` 未检测到目标对象（如事务快照延迟），`replace` 策略也会执行全部三种 DROP：

```python
elif strategy == 'replace':
    # 安全兜底 — IF EXISTS 保证不会报错
    pg_cursor.execute(f"DROP VIEW IF EXISTS {qualified_view} CASCADE")
    pg_cursor.execute(f"DROP MATERIALIZED VIEW IF EXISTS {qualified_view} CASCADE")
    pg_cursor.execute(f"DROP TABLE IF EXISTS {qualified_view} CASCADE")
    pg_conn.commit()
```

`IF EXISTS` 确保对象不存在时不会报错，`CASCADE` 确保依赖关系一并清除。

### 2.4 基表依赖预检查（新增）

**新增函数**：`_check_view_dependencies`

在 `CREATE VIEW` 执行前，扫描视图 SQL 中的 `FROM` / `JOIN` 表引用，与目标 schema 现有表名列表对比，提前预警缺失的基表：

```python
# 预取目标 schema 所有表/视图名
target_tables = {row[0].lower() for row in pg_cursor.fetchall()}

# 扫描视图 SQL 中的表引用
ref_pattern = re.compile(
    r'\b(?:FROM|JOIN)\s+(?:[\w]+\.)?([a-zA-Z_][a-zA-Z0-9_]*)',
    re.IGNORECASE,
)
```

**输出示例**：
```
[INFO] 目标 schema efmis_ksd_2010ys 现有表/视图数: 45
[WARN]   依赖预检: 视图 SQL 引用了目标 schema 不存在的表: acct_t_vchrno
[WARN]   提示: 请先迁移上述基表到 efmis_ksd_2010ys,否则 CREATE VIEW 会报"关系不存在"
```

**注意**：此预检查为**启发式**（非完整 SQL 解析），可能产生误报（如子查询别名被误识别为表名）。预检查不会阻止 `CREATE VIEW` 执行，仅提供前置预警。

### 2.5 增加"已经存在"错误诊断

当 `CREATE VIEW` 仍报「已经存在」时（存在性检查漏网的极端情况），增加诊断提示：

```python
elif '已经存在' in err_msg or 'already exists' in err_msg.lower():
    make_warn_log(log, f'  可能原因: 目标对象已存在但未被存在性检查捕获')
    make_warn_log(log, f'  建议: 手动执行 DROP 后重试,或将冲突策略改为 replace')
```

## 四、用户操作建议

### 4.1 修复「已经存在」错误

**方案 A（推荐）**：将冲突策略改为 `replace`
- 创建任务时选择冲突策略 → `替换(replace)`
- 系统会自动 DROP 旧对象后重建

**方案 B**：手动清理残留对象
```sql
-- 在目标库执行，检查残留对象
SELECT relname, relkind FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'efmis_ksd_2010ys' AND relname LIKE 'efmis_ksd_2010ys_%';

-- 手动 DROP
DROP TABLE "efmis_ksd_2010ys"."efmis_ksd_2010ys_aa" CASCADE;
```

### 4.2 修复「关系不存在」错误

1. 查看日志中的 `[WARN] 依赖预检` 行，获取缺失基表列表
2. 先完成基表迁移（任务类型选「表」）
3. 基表迁移完成后再重试视图迁移

### 4.3 多视图迁移建议

- 多视图迁移前先迁移所有基表，再迁视图
- 使用 `replace` 冲突策略，避免残留对象冲突
- `error` 策略下单个失败不会中断整批（v2.3.2 修复后）
