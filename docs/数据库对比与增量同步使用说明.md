# 数据库对比与增量同步使用说明

> v2.4 新增「对比预览」与「立即增量同步」功能,支持对 Oracle→PolarDB-PG 的表进行近实时数据同步。
> 底层复用主键对齐(pk_mirror)增量同步机制,API 层提供只读对比与一键同步能力。

## 一、功能概述

| 功能 | 说明 | 是否写操作 |
|------|------|-----------|
| **对比预览** | 只读对比源/目标差异,返回待插入/待删除/共存行数 | 否(只读) |
| **立即增量同步** | 同步执行主键对齐:补插缺失行、删除多余行、检测并更新变更行 | 是(写目标库) |
| **定时增量同步** | Celery Beat 每 5 分钟扫描启用定时的 pk_mirror 任务 | 是(写目标库) |

**适用场景**:
- 割接前数据预同步(减少最终停机时间)
- 持续增量保持(源库有变更,定期同步到目标)
- 数据校验(对比预览查看差异规模)

**不适用场景**:
- 毫秒级实时同步(需 Oracle CDC/LogMiner,本项目不支持)
- 无主键表(主键对齐依赖主键,无主键请用「按水位列」增量)
- 超大表(单次对比上限 `sync_max_pkey_rows`,默认 50 万行)

## 二、使用前提

1. **任务类型**:table / view_to_table / all_tables / table_batch
2. **增量模式**:pk_mirror(主键对齐)
3. **源表必须有主键**:主键对齐依赖主键列做差集对比
4. **行数限制**:源/目标行数不超过 `sync_max_pkey_rows`(默认 50 万,可调大)

## 三、对比预览(只读)

### 3.1 前端操作

任务详情页 → 「对比预览」按钮(蓝色,表类型任务且配置了 PG 连接时显示)。

点击后:
- 按钮显示「对比中...」(loading)
- 对比完成后,按钮下方展示差异卡片:
  - 源表行数 / 目标表行数
  - 待插入(源有目标无,N 行)
  - 待删除(目标有源无,N 行)
  - 两端共存(N 行)
  - 主键列
  - 备注(UPDATE 检测需同步时做)

### 3.2 API 调用

```http
GET /api/tasks/<task_id>/compare-preview/
Authorization: Bearer <token>
```

**响应示例**:
```json
{
  "status": "ok",
  "diff": {
    "source_schema": "SCOTT",
    "table_name": "EMP",
    "target_schema": "scott",
    "pg_table": "emp",
    "target_exists": true,
    "source_count": 10050,
    "target_count": 10000,
    "to_insert": 50,
    "to_delete": 0,
    "common": 10000,
    "sampled_updates": null,
    "pk_columns": ["EMPNO"],
    "note": "UPDATE 检测需逐行哈希对比(开销大),将在同步时执行;此处仅统计主键差集"
  }
}
```

**特殊情况返回**:
- 目标表不存在:`to_insert = source_count`,`note` 提示需先全量迁移
- 源表无主键:`to_insert/to_delete/common = null`,`note` 提示改用水位列增量
- 行数超限:`to_insert/to_delete/common = null`,`note` 提示调大上限或改用水位列

## 四、立即增量同步

### 4.1 前端操作

任务详情页 → 「立即增量同步」按钮(绿色,仅 `incremental_mode=pk_mirror` 任务显示)。

点击后:
1. 弹出确认框,说明将执行的操作与适用范围
2. 确认后按钮显示「同步中...」(同步执行,阻塞等待)
3. 完成后弹出结果(耗时 + 最后 5 行日志)
4. 自动刷新任务详情

### 4.2 API 调用

```http
POST /api/tasks/<task_id>/sync-now/
Authorization: Bearer <token>
```

**响应示例(成功)**:
```json
{
  "status": "ok",
  "duration_seconds": 12.53,
  "log_tail": [
    "【主键对齐】主键列 EMPNO;源 10050 行 / 目标 10000 行;开始对比…",
    "【主键对齐】待删除 0 行,待插入 50 行,两端共存 10000 行(需检测 UPDATE)。",
    "【主键对齐】本轮处理插入批次结束(计划插入 50 行)。",
    "【主键对齐】UPDATE 检测完成,共更新 3 行(两端共存 10000 行)。"
  ]
}
```

**错误响应**:
```json
{
  "status": "error",
  "message": "【主键对齐】源表 600000 行、目标表 590000 行,超过单次上限 500000 行..."
}
```

### 4.3 同步执行逻辑

`sync_now` 同步执行(非异步),流程:

1. 获取 Oracle/PG 连接(从连接池)
2. 调用 `run_table_pk_mirror_flow`:
   - 目标表不存在 → 自动全量建表+导数(首次)
   - 目标表存在 → 主键对齐:
     - 拉取两端主键,计算差集
     - **待删除**(目标有源无):分批 DELETE
     - **待插入**(源有目标无):按主键查源全列,分批 INSERT
     - **待更新**(两端共存):逐行哈希对比,差异行 UPDATE
3. 返回耗时与日志尾

**超时风险**:gunicorn `--timeout 120`,中小表(50 万行内)可在 120s 内完成。大表会超时,请改用定时增量。

## 五、定时增量同步(Celery Beat)

对大表或需持续同步的场景,配置定时增量:

### 5.1 创建任务时配置

- 增量模式:pk_mirror
- 启用定时增量:`schedule_enabled = true`
- 调度最小间隔:`schedule_interval_minutes`(默认 60 分钟)

### 5.2 Celery Beat 自动扫描

settings.py 已配置 Beat 任务:

```python
CELERY_BEAT_SCHEDULE = {
    'scan-scheduled-migrations': {
        'task': 'migration_app.tasks.beat_scan_scheduled_migrations',
        'schedule': float(os.environ.get('MIGRATION_BEAT_SCAN_SECONDS', '300')),
    },
}
```

Beat 每 5 分钟扫描 `schedule_enabled=true` 且到达 `schedule_interval_minutes` 的 pk_mirror 任务,自动触发增量同步。

### 5.3 缩短间隔(近实时)

修改环境变量 `MIGRATION_BEAT_SCAN_SECONDS=60`(1 分钟扫描)和任务 `schedule_interval_minutes=1`,实现分钟级近实时同步。

> 注意:频率越高,Oracle 负载越大。建议根据源库负载能力调整。

## 六、对比预览 vs 立即同步 vs 定时同步

| 维度 | 对比预览 | 立即增量同步 | 定时增量同步 |
|------|---------|-------------|-------------|
| 触发方式 | 手动(前端按钮) | 手动(前端按钮) | 自动(Beat) |
| 写操作 | 否(只读) | 是 | 是 |
| 执行方式 | 同步(秒级) | 同步(秒~分钟级) | 异步(Celery) |
| UPDATE 检测 | 否(仅主键差集) | 是(逐行哈希) | 是(逐行哈希) |
| 适用场景 | 评估差异规模 | 中小表即时同步 | 大表/持续同步 |
| 行数限制 | sync_max_pkey_rows | sync_max_pkey_rows | sync_max_pkey_rows |

## 七、限制与注意事项

1. **主键必须**:pk_mirror 依赖源表主键。无主键表会返回错误,建议改用「按水位列」增量(`incremental_mode=timestamp` + `watermark_column`)。

2. **行数上限**:`sync_max_pkey_rows` 默认 50 万。两端行数均不得超过,否则拒绝执行(防 OOM)。大表调大此值或改用水位列增量。

3. **UPDATE 检测开销**:两端共存行需逐行哈希对比(全列 `to_char` 拼接 + MD5)。共存行数多时,同步耗时主要花在 UPDATE 检测上。

4. **立即同步超时**:`sync_now` 同步执行,gunicorn timeout 120s。若表较大接近超时,改用定时增量(Celery 异步,无 HTTP 超时限制)。

5. **并发安全**:已实现两层保护,避免并发主键对齐冲突:
   - **前端**:任务状态为 `running` 时,「立即增量同步」按钮自动禁用并提示「执行中不可同步」
   - **后端**:`sync_now` 接口检测到 `status=running` 时返回 409 Conflict,拒绝执行
   - **建议**:高频定时任务(Beat)与手动 `sync_now` 仍可能并发,建议低频定时 + 按需手动

## 八、底层实现

### 8.1 对比预览

**文件**: [incremental_sync.py:preview_table_diff](../migration_app/incremental_sync.py#L65)

只读对比,复用 `run_table_pk_mirror_flow` 的对比部分(拉主键、算差集),不执行 DELETE/INSERT/UPDATE。

### 8.2 立即同步

**文件**: [api.py:sync_now](../migration_app/api.py#L397)

获取连接 → 调用 `run_table_pk_mirror_flow` → 写任务日志 → 返回结果。

### 8.3 主键对齐算法

1. 拉取两端全主键(分批 fetchmany 20000)
2. 主键差集:
   - `to_delete = PG主键集 - Oracle主键集`(目标多余)
   - `to_insert = Oracle主键集 - PG主键集`(源有目标无)
   - `common = 交集`(两端共存)
3. DELETE:分批 500 行,`WHERE pk IN (...)`
4. INSERT:分批 100 行,按主键查 Oracle 全列,`executemany`
5. UPDATE 检测:对 common 分批,两端查全列 `to_char` + MD5 哈希,差异行 UPDATE

详细实现见 [incremental_sync.py](../migration_app/incremental_sync.py)。
