# Oracle → PolarDB(PG) 迁移能力分析与改善方案

> 分析日期：2026-08-20（v2.4.2 已实施 P0 全部修复，见文末「实施记录」）
> 分析范围：`migration_app/` 全模块（schema_converter、oracle_sql_converter、view_materialization、trigger_export、full_database、views、data_writer、oracle_row_adapter 等）
> 结论速览：项目已覆盖 **序列 / 物理表 / 外键回放 / 视图（定义+物化）/ 物化视图 / 触发器 / 例程** 七类对象的整库编排迁移，但存在 **① 类型映射精度缺陷、② 视图/SQL 语法转换覆盖不足、③ 触发器仅导出不迁移、④ 整库编排的状态覆盖 bug、⑤ 性能与校验短板** 五大类问题。下文逐项列出并给出改善方案（P0 最高优先级）。

---

## 1. 各对象类型迁移现状与问题清单

### 1.1 能力矩阵

| 对象类型 | 迁移方式 | 关键代码 | 主要问题等级 |
|---|---|---|---|
| 物理表 | 结构 DDL + 分批导数 + 后置 Schema 扩展 | `views.py:828 _migrate_single_table` | 中（类型映射细节） |
| 序列 | ALL_SEQUENCES → CREATE SEQUENCE | `views.py:1948 _migrate_one_sequence` | 低 |
| 外键 | 数据导入完成后统一回放 | `schema_converter.py:551` | 低 |
| 视图 | definition 模式（CREATE VIEW）或 materialize 模式（物化为表） | `views.py:448`、`view_materialization.py` | **高**（语法转换不足） |
| 物化视图 | 定义转换后 CREATE MATERIALIZED VIEW | `views.py:279` | **高**（刷新机制丢失） |
| 触发器 | **仅导出源码 + PL/pgSQL 模板，不自动创建** | `trigger_export.py` | **高**（无自动迁移） |
| 例程 | 安全检测通过才执行，否则仅导出 | `views.py:642 migrate_routine` | 高（PL/SQL 几乎必然需人工） |
| 同义词 / 包 / DBLink / 分区DDL | 不迁移，仅告警 | `full_database.py:143` | 中 |

### 1.2 物理表（含类型映射）问题

**实现位置**：`views.py:1502 convert_oracle_to_pg_type`、`views.py:828 _migrate_single_table`

| # | 问题 | 说明 | 等级 |
|---|---|---|---|
| T1 | `NUMBER` 无精度 → `NUMERIC` | 全列 NUMERIC 性能差、索引/比较语义变化。无精度 NUMBER（Oracle 为"最大38位浮点"）建议映射 `DOUBLE PRECISION` 或保留 NUMERIC 但记入报告 | 中 |
| T2 | `TIMESTAMP WITH LOCAL TIME ZONE` → `TIMESTAMPTZ` 近似 | 语义不同：WLZ 存储归一化为 DB 时区、会话时区呈现。TIMESTAMPTZ 会随 session TimeZone 改变显示，迁移时若两端时区不一致会产生数据偏移，需在报告中标注会话时区假设 | 中 |
| T3 | `CHAR(n)` 空白填充语义差异 | Oracle CHAR 比较忽略尾随空格，PG 不忽略，且 Oracle CHAR 内容超长会截断而 PG 报错。建议评估转 `VARCHAR(n)` 或加迁移前长度校验 | 中 |
| T4 | 空字符串与 NULL | Oracle `''` 即 NULL，PG 区分。源端若存在 `''` 字面量/默认值，行为不同。当前转换器无任何处理 | 中 |
| T5 | `FLOAT(p)` p≤24 → `REAL` | Oracle FLOAT 是 NUMBER 的变体（十进制语义、无浮点误差），PG REAL 是 IEEE 浮点。金融场景 p≤24 数据可能出现精度差异，建议统一 `DOUBLE PRECISION` 或 `NUMERIC` | 中 |
| T6 | IDENTITY 列 START 值未同步 | `views.py:938` 生成 `GENERATED BY DEFAULT AS IDENTITY` 但未读取 Oracle `ALL_TAB_COLUMNS.IDENTITY_OPTIONS` 的 START WITH 增量值。迁移后目标表自增从 1 开始，若源端已用至 1e6，新插入将主键冲突 | **高** |
| T7 | 虚拟列表达式转换薄弱 | `views.py:944` 用 `convert_oracle_to_pg_sql` 转换 DATA_DEFAULT，若含未覆盖语法（DECODE 之外的 Oracle 函数）则建表直接失败 | 中 |
| T8 | 分区表按普通表迁移 | Discovery 仅告警（`full_database.py:171`），分区键、分区/子分区 DDL、本地索引全部丢失，大表场景性能影响大 | **高** |
| T9 | 未知类型静默降级 TEXT | `views.py:1641` 仅写 warning 日志。`SDO_GEOMETRY`、`ORDSYS.*` 等空间/媒体类型会变成 TEXT 且数据可能无法抽出 | 中 |
| T10 | 表级 DEFAULT 中 `SYSDATE` 转为 `CURRENT_TIMESTAMP`（`schema_converter.py:89`） | Oracle `CURRENT_DATE` 被误转成 `CURRENT_TIMESTAMP`（丢失"仅日期"语义），应转 PG `CURRENT_DATE` | 低 |

### 1.3 视图问题

**实现位置**：`views.py:448 _migrate_view_definition`（definition 模式）、`view_materialization.py`（materialize 模式）、`oracle_sql_converter.py`（语法转换）

**definition 模式的语法转换缺陷**（这是视图失败的最大来源）：

| # | 问题 | 说明 | 等级 |
|---|---|---|---|
| V1 | `(+)` 外连接不转换 | `oracle_sql_converter.py:11` 仅把 `(+)` 列入人工审查清单，不自动改写为 `LEFT/RIGHT JOIN`。含 `(+)` 的视图 100% 建失败 | **高** |
| V2 | `CONNECT BY / START WITH` 不转换 | 层次查询无自动改写（`WITH RECURSIVE`），仅告警 | **高** |
| V3 | `ROWNUM` 转换不正确 | `views.py` 转换器 `_replace_rownum` 将 `ROWNUM` 替换为 `ROW_NUMBER() OVER()`：① 无 `ORDER BY` 时行号不确定，与 Oracle 返回顺序可能不同；② `ROWNUM <= N` 分页写法会生成 `ROW_NUMBER() OVER() <= N`——**语法直接报错**（窗口函数不能用于 WHERE），需改写为子查询 + FETCH FIRST | **高** |
| V4 | `_replace_to_char` 单参数替换正则误伤 | `oracle_sql_converter.py:331` 的 `TO_CHAR\(\s*([^)]+?)\s*\)` 用 `[^)]+` 匹配，参数中含嵌套括号（如 `TO_CHAR(NVL(a,b))`）时匹配失败或截断；双参数正则 `[^,()]+` 同样无法处理参数含逗号（如 `TO_CHAR(d, 'YYYY"年"MM')` 没问题，但 `TO_CHAR(decode(x,1,'a','b'), 'FM999')` 失败） | 中 |
| V5 | `_replace_to_date` 仅支持字面量 | `TO_DATE(列, 格式)` 不转换，且 Oracle→PG 日期格式串差异（`RR`、`HH24:MI:SS AM`、`J` 等）完全未处理，格式串不兼容时运行时报错 | 中 |
| V6 | `MINUS` / `INTERSECT` 未转换 | `MINUS` 在 `detect_manual_review_items` 中有检测但无替换（PG 用 `EXCEPT`），一行正则即可解决却留给人工 | 中 |
| V7 | 大量常用函数未覆盖 | `TRUNC(date)`、`ADD_MONTHS`、`MONTHS_BETWEEN`、`LAST_DAY`、`NEXT_DAY`、`INSTR`（4参数）、`SUBSTR`（负数索引语义同，但 `SUBSTR(col, -n)` 长度参数差异）、`SYS_CONTEXT`、`USER`、`UID`、`SYS_GUID()`、`RAWTOHEX/HEXTORAW`、`REGEXP_LIKE`（PG 需 `~`）、`CASE` 中 `NVL` 已覆盖但 `LNNVL`、`DECODE` 之外的 `NANVL` 等均未处理 | 中 |
| V8 | 标识符引用不带 schema 修正 | 视图 SQL 中引用其他 schema 的表（`OTHER_SCHEMA.T`）时，仅设置 `search_path`（`views.py:497`）不够——跨 schema 引用不会命中目标 schema 映射，建视图报"关系不存在" | 中 |
| V9 | 视图间依赖无拓扑排序 | 全库迁移 views 阶段按 `ORDER BY VIEW_NAME` 字母序处理（`full_database.py:67`），视图 B 依赖视图 A 但 B 字母序在前时 CREATE 失败，失败后无自动重试 | **高** |
| V10 | `CREATE VIEW` 失败仅记录日志 | `views.py:595` 失败原因提示依赖人工，整库场景下失败视图不会进入"依赖重排重试"环节 | 中 |

**materialize 模式**：整体实现较完善（分批、进度、取消、截断自动扩 TEXT，`view_materialization.py:289`），主要缺口：
- 物化后不迁移视图的依赖注释/授权；
- 目标表只有列结构，无主键/索引，增量同步阶段无法高效对比。

### 1.4 物化视图问题

**实现位置**：`views.py:279 migrate_materialized_view`

| # | 问题 | 等级 |
|---|---|---|
| M1 | 仅建 `CREATE MATERIALIZED VIEW ... AS <查询体>`，查询体语法转换与普通视图共用同一套（V1–V8 全部适用） | **高** |
| M2 | 刷新机制丢失：Oracle `REFRESH FAST/COMPLETE/FORCE ON COMMIT/ON DEMAND`、物化视图日志（MLOG$）、`NEXT` 定时调度均未迁移；PG 侧未建 `REFRESH ... ` 任务，也未提供 `WITH NO DATA` 选项（大表物化视图 CREATE 时会先全量跑一遍查询，可能超时） | **高** |
| M3 | 物化视图上的索引未迁移（Oracle 常在 MV 上建索引支撑查询） | 中 |
| M4 | `REFRESH FAST` 依赖的唯一约束/ROWID 未映射为 PG `REFRESH MATERIALIZED VIEW CONCURRENTLY` 所需的 `WITH NO DATA` + 唯一索引要求，未做前置检查 | 中 |

### 1.5 触发器问题

**实现位置**：`trigger_export.py`

| # | 问题 | 等级 |
|---|---|---|
| G1 | **完全不自动迁移**：只生成 `-- TODO` 模板函数（`trigger_export.py:125`），业务逻辑全部留空。整库迁移后目标库无任何触发器生效，若源端触发器承担审计/派生列/序列赋值职责，业务数据将不一致且**无告警汇总**（仅日志提示） | **高** |

### 1.6 全库迁移（full_database）流程问题

**实现位置**：`full_database.py:234 migrate_full_database`

| # | 问题 | 说明 | 等级 |
|---|---|---|---|
| F1 | **编排状态被单视图任务覆盖（断点续传失效 bug）** | views/mviews/routines 阶段通过修改共享 task 的 `source_schema/source_object` 再调用 `views.migrate_view(task.id)`（`full_database.py:441-445`）。而 `migrate_view` → `run_view_materialization_task` 会写 `task.view_progress = {视图名: ...}`（`view_materialization.py:328-339`），**把整库编排存在 view_progress 里的 `completed_objects/phase/phase_index` 整个覆盖掉**。若任务在 views 阶段中断，续传时 `vp.get('phase')` 丢失，resume 语义损坏 | **高** |
| F2 | 视图/物化视图无依赖拓扑排序 | 同 V9；表有 `_topological_sort_tables_by_fk`（`views.py:743`）但视图没有对应实现 | **高** |
| F3 | 触发器/例程阶段"成功"标准失真 | 触发器只要导出源码就算 `trg_ok`；例程只要没抛异常就算成功（即使实际走了"仅导出未执行"分支）。最终状态 `completed` 会误导用户以为对象已可用 | **高** |
| F4 | 单任务串行 + 共享 task 字段写竞争 | 表阶段有 `migrate_all_tables` 的并行路径（`parallel_tables.py`），但整库编排内表是串行 for 循环；且 views 阶段反复 `task.save(update_fields=[...source_object...])` 若同一 task 被用户在 UI 同时操作会产生覆盖 | 中 |
| F5 | `failed_objects` 无重试入口 | 失败对象记录在 view_progress JSON 里，但没有"仅重试失败对象"的一键操作，续传按 `completed_objects` 差集重跑，语义可行但 UI 未暴露 | 中 |
| F6 | 日志全量重写性能问题 | 每个对象/进度点都 `task.log = '\n'.join(log)` 全量保存（`views.py:817`），整库几千对象时 log 文本与 DB 写放大显著 | 低 |
| F7 | 例程排序问题 | routines 按 OBJECT_NAME 排序，函数间调用依赖未排序；PG 创建时被调用函数不存在会失败（可后续补建，但未自动重试） | 中 |
| F8 | 触发器在数据迁移后导出但从未在目标库创建 | 与 G1 呼应：编排顺序正确（数据→触发器），但最后一步缺失 | **高** |

### 1.7 数据迁移与任务过程问题

| # | 问题 | 说明 | 等级 |
|---|---|---|---|
| D1 | COPY 路径的 bytea 编码 bug | `data_writer.py:27` `'\x' + value.hex()`：PG COPY **文本格式**的 `\x` 转义只消费紧跟的**两个**十六进制字符，多字节 bytes（如 `b'ab'` → `\x6162`）会被解析成 `\x61` + 字面量 `62`，**BLOB 数据经 COPY 写入即损坏**。应改为 `value.hex()` 逐字节 `\xNN\xNN...` 或改用 `psycopg2` 的 `copy_expert` 二进制格式 | **高** |
| D2 | COPY 路径无事务回滚一致性校验 | COPY 失败由上层 rollback，但 `_format_copy_value` 未处理字段内 `\\.` 结束符等边缘情况 | 低 |
| D3 | 序列 START WITH 用 `LAST_NUMBER` | `views.py:2031`：LAST_NUMBER 是"已刷入缓存的上界"，通常 ≥ 实际已用值，作为 START 一般安全；但 CACHE 很大时（如 CACHE 10000）会跳号，若业务要求连续需提示。另外应在表数据导入后再次 `setval` 对齐 IDENTITY/序列（见 T6） | 中 |
| D4 | 校验仅行数比对 | `migration_validation.validate_row_counts` 只 COUNT(*)。NULL/空串差异（T4）、时区偏移（T2）、浮点差异（T5）均无法发现，建议增加抽样 checksum（如按主键抽样比较 `md5(行文本)`） | 中 |
| D5 | 逐约束/逐索引/逐注释 commit | `schema_converter.py` 中每个 ALTER/CREATE/COMMENT 单独 commit，上千列注释时缓慢；可合并为每表一个事务 | 低 |
| D6 | `task.refresh_from_db()` 每批次执行 | `_migrate_single_table` 每个 fetch 批次都 refresh task（`views.py:1046`），大表百万行时产生大量元数据查询；建议按进度保存间隔节流 | 中 |
| D7 | 取消依赖轮询 task 表 | 取消检测与进度保存绑定，无事件机制，最长延迟一个批次 | 低 |

## 2. 改善方案

### P0（正确性缺陷，必须修）

#### P0-1 修复整库编排 view_progress 覆盖 bug（F1）
- **位置**：`view_materialization.py:328-345` 与 `full_database.py:540-551`。
- **方案**：单视图进度不再直接赋值 `task.view_progress = {...}`，改为读-合并-写：
  ```python
  vp = task.view_progress or {}
  if isinstance(vp, str): vp = json.loads(vp)
  vp.setdefault('per_view', {})[view_name] = {...}   # 编排字段(orchestration/phase/completed_objects)保留在顶层
  task.view_progress = vp
  ```
  同理修复 `_migrate_single_table`（`views.py:1092`）对 view_progress 的整体覆盖。回归测试：整库迁移在 views 阶段人工中断 → resume 后应从断点继续而非重跑。

#### P0-2 修复 COPY bytea 编码（D1）
- **位置**：`data_writer.py:20-34`。
- **方案**：`isinstance(value, bytes): return ''.join(f'\\x{b:02x}' for b in value)`；并补一条端到端测试：含多字节 BLOB 的表走 COPY 阈值路径，迁移后 `octet_length` 与源端比对。

#### P0-3 IDENTITY / 序列值与数据对齐（T6、D3）
- **方案**：`apply_post_table_schema`（`schema_converter.py:397`）末尾追加：
  1. 若表含 IDENTITY 列：`SELECT setval(pg_get_serial_sequence('tbl','col'), GREATEST((SELECT MAX(col) FROM tbl), 1))`；
  2. 解析 `ALL_TAB_COLUMNS.IDENTITY_OPTIONS` 的 `START WITH` 写入 `GENERATED BY DEFAULT AS IDENTITY (START WITH n)`；
  3. 普通序列绑定列（`_SEQ_DEFAULT_RE`）同样在数据导入后 `setval` 到 `MAX(列值)`。

#### P0-4 ROWNUM 分页/过滤正确转换（V3）
- **方案**：在 `oracle_sql_converter.py` 中区分三种用法：
  - `ROWNUM <= / < N`（WHERE 中）→ 外包一层 `SELECT * FROM (...) FETCH FIRST N ROWS ONLY`；
  - SELECT 列表中的 `ROWNUM` → `ROW_NUMBER() OVER (ORDER BY <迁移排序提示或告警>)`，并在 manual_items 标注"行序与 Oracle 不保证一致"；
  - `ROWNUM = 1` → `FETCH FIRST 1 ROWS ONLY`。
  实现建议：先用括号平衡扫描（复用 `_replace_decode_once` 的扫描器）定位 WHERE 子句中的 ROWNUM 谓词再改写，避免纯正则误伤。

#### P0-5 触发器迁移结果显式化（F3、G1）
- **方案**：
  1. 整库报告中将"仅导出未执行"的触发器/例程单列为 `skipped_manual` 状态，任务终态在存在此类对象时置 `partial`（而非 completed），并在 UI 显著提示；
  2. 触发器模板中对"语句级 + WHEN 引用 NEW/OLD"（G2）与"INSTEAD OF 基对象非视图"（G3）在生成期检测并注释说明，避免用户直接执行报错；
  3. 中期目标：把 `trigger_export` 升级为"常见模式自动改写"——对 `BEFORE INSERT ... :NEW.id := seq.NEXTVAL`（占 Oracle 触发器大头）自动生成完整 PL/pgSQL（setval/nextval），其余保持模板导出。

### P1（提升迁移成功率）

#### P1-1 引入真正的 SQL 解析层替换正则替换（V4、V1）
- 现状：`oracle_sql_converter.py` 全部为正则/手写扫描，嵌套函数参数必然误伤。
- 方案：接入 `sqlglot`（纯 Python，支持 Oracle 方言 parse → postgres 方言 emit）：
  ```python
  import sqlglot
  pg_sql = sqlglot.transpile(oracle_sql, read='oracle', write='postgres')[0]
  ```
  - 将现有手写替换作为 sqlglot 解析失败时的回退路径；
  - `(+)`、`MINUS→EXCEPT`、`DECODE`、`NVL` 等大部分可由 sqlglot 直接完成；
  - 解析失败或含 `CONNECT BY/PIVOT/MODEL` 的输出进人工清单（保留 `detect_manual_review_items`）。
- 依赖成本低（pip 一包），收益覆盖视图/物化视图/虚拟列/约束 CHECK 全链路。

#### P1-2 视图依赖拓扑排序 + 失败重排重试（V9、F2、F7）
- 方案：新增 `views.py::_topological_sort_views`：
  1. 用 `ALL_DEPENDENCIES`（OWNER/NAME/REFERENCED_OWNER/REFERENCED_NAME/REFERENCED_TYPE IN ('VIEW','TABLE')）建图；
  2. Kahn 拓扑排序（复用表排序的 heap 实现）；
  3. views 阶段按排序结果处理；
  4. 一轮结束后对失败视图再做一轮"依赖已就绪"重试（最多 2 轮），仍失败的进 failed_objects。
  routines 阶段可用 `ALL_DEPENDENCIES`（REFERENCED_NAME 指向函数）做同样处理。

#### P1-3 类型映射策略增强（T1、T2、T5、T9）
- 方案：`convert_oracle_to_pg_type` 增加可选 `strict` 策略参数并生成《类型映射差异报告》：
  - NUMBER 无精度 → 默认 `NUMERIC`，报告标注可选 `DOUBLE PRECISION`；
  - `FLOAT(p)` → 统一 `DOUBLE PRECISION`（消除 REAL 精度差异）；
  - `WITH LOCAL TIME ZONE` → 迁移前记录源/目标 `SESSIONTIMEZONE`，写入报告并在任务日志 WARN；
  - 未知类型 → 报告列出 schema/表/列/类型全集，而非散落日志。

#### P1-4 物化视图刷新机制补偿（M2、M3）
- 方案：
  1. `CREATE MATERIALIZED VIEW ... WITH NO DATA` 可配置（大 MV 建议默认），随后显式 `REFRESH MATERIALIZED VIEW`（可离峰执行）；
  2. 解析 Oracle `ALL_MVIEWS.REFRESH_METHOD/REFRESH_MODE/NEXT_SYSDATE`，生成对应建议（PG 无 FAST 增量刷新，标注需改 `CONCURRENTLY` + 唯一索引或使用 pg_ivm 扩展——PolarDB 兼容 PG 生态可直接评估）；
  3. 迁移 MV 上的索引（复用 `fetch_table_indexes`，ALL_INDEXES 对 MV 同样可见）。

#### P1-5 常用函数转换补齐（V6、V7）
在引入 sqlglot 之前，先低成本补齐高 replacements（正则安全、单行替换）：
- `MINUS` → `EXCEPT`（注意排除标识符含 MINUS 的场景，用 `\bMINUS\b` + 上下文在 set 操作位置）；
- `SYSDATE` 已有；补 `SYSTIMESTAMP → CURRENT_TIMESTAMP`、`USER → CURRENT_USER`；
- `ADD_MONTHS(d,n) → (d + (n || ' month')::interval)`、`MONTHS_BETWEEN(a,b) → (EXTRACT(EPOCH FROM a) - EXTRACT(EPOCH FROM b)) / 2629800.0`（或 `months_between` 兼容函数）、`LAST_DAY(d) → (date_trunc('month', d) + interval '1 month - 1 day')::date`；
- `REGEXP_LIKE(col, pat) → col ~ pat`；
- `SYS_GUID() → gen_random_uuid()::text`（报告标注格式差异）。
每条都应同步加入测试（`tests.py` 目前对转换器覆盖不足）。

### P2（性能与体验）

#### P2-1 表级并行迁移扩展到整库编排（F4）
- 复用 `parallel_tables.py` 的并行框架，把 full_database 的 tables 阶段改为按表并行（受连接池上限约束，默认 4 并发）；FK 回放阶段已在数据后执行，不受并行影响。注意并行时 `completed_objects` 更新需加锁（或迁移到 DB 表 `migration_object_state`，顺带解决 F5 的失败重试 UI）。

#### P2-2 失败对象一键重试（F5）

#### P2-3 日志分片存储（F6）

#### P2-4 校验增强（D4）

#### P2-5 杂项

- `task.refresh_from_db()` 节流（D6）：仅当 `total_rows - last_refresh >= interval` 时刷新取消标志。

### 6.1 新增高危问题

| # | 问题 | 位置 | 说明 | 等级 |
|---|---|---|---|---|
| H1 | **哈希表达式对数值列必然报错，UPDATE 检测形同虚设** | `migration_validation.py:270-278`、`incremental_sync.py:_detect_and_apply_updates` | 两端哈希对所有列统一套 `to_char(col,'YYYY-MM-DD HH24:MI:SS')` 日期格式串。对 NUMBER/数值列，Oracle 报 **ORA-01481（无效数字格式模型）**、PG 的 to_char 数值模板同样无效 → 整段哈希对比走异常分支。后果分两处：① 增量同步的 UPDATE 检测失效（差异行不会 UPDATE，**数据静默漂移**）；② `validate_row_hashes` 永远返回 None 跳过。含数值列的表（几乎所有业务表）全部命中 | **高** |
| H2 | **LOB 读取失败静默置 NULL，数据丢失不可见** | `oracle_row_adapter.py:61-64` | `value.read()` 异常时仅 `logger.warning` 后返回 None。该行仍会插入（内容为 NULL），行数校验照样通过——损坏的 BLOB/CLOB 完全无法通过现有校验发现。同理 `utf-8 errors='replace'`（75 行）静默替换损坏字符 | **高** |
| H3 | **高级校验功能已实现但从未接线** | `migration_validation.py` | `validate_aggregates` / `validate_row_hashes` / `validate_sample_rows` / `validate_full` 在整个代码库中**没有任何调用方**。迁移主流程只调 `validate_row_counts`（行数比对）。D4 指出的"校验仅行数"实际上比预想更严重：修复方案已经写好了，只是没接 | **高** |

### 6.3 改善方案（补充第 2 节）

#### P0-6 按列类型分派哈希格式化（修 H1）
- 将 `to_char(col, fmt)` 的统一模板改为按 `ALL_TAB_COLUMNS.DATA_TYPE` 分派：
  - 日期/时间戳 → `to_char(col,'YYYY-MM-DD HH24:MI:SS.FF6')`（两端一致，含微秒）；
  - 数值 → Oracle `to_char(col,'FM9999999999999999999999990.0999999999')` ↔ PG `to_char(col,'FM9999999999999999990.0999999999')`，或两端直接 `trim(to_char(...))` 归一；
  - 字符 → Oracle `col`、PG `col`（注意 NULL 归一为 `''` 已有 NVL/COALESCE 处理）；
  - BLOB/RAW → 排除出哈希列或用 `md5(rawtohex(col))` / PG `md5(encode(col,'hex'))`；
  - 无法归一的类型（interval/boolean）跳过并在日志列明。
- 同步修复 `validate_row_hashes` 与 `_detect_and_apply_updates` 两处（共用一个表达式构建函数，消除复制粘贴）。

#### P0-7 LOB 读取失败显式失败（修 H2）
- `adapt_oracle_value_for_postgres` 不再吞异常：读失败计数 + 抛 `MigrationDataError`（或按平台配置 `lob_error_policy=strict|warn`，默认 strict）。decode 也去掉 `errors='replace'`，改 `errors='strict'` 并纳入同一策略。

#### P0-8 接线高级校验（修 H3）
- `_migrate_single_table` 行数校验后按平台配置调用 `validate_full`：小表（≤10 万行）开哈希，大表开聚合+抽样；strict 模式由任务字段控制。现有函数签名已兼容，主要是调用与配置项工作。

#### P1-6 增量同步健壮性（修 N1/N2/N7）
- 主键差集改分块（按 PK 范围 5 万一块）流式对比，内存占用降为 O(块)；
- UPDATE 扫描达上限时在 `view_progress` 写入 `sync_pending_updates=True`，任务状态置 partial，下轮续扫；
- Oracle 连接统一设置 `encoding='UTF-8'` / NLS，消除 N7。

#### P1-7 校验数值容差与类型化主键比较（修 N3/N4）
- 容差改相对式；抽样校验 PG 端按列类型用 `%s` 原生绑定（datetime/numeric 直接绑参数，不走 `::text`）。

#### P2-6 配置联动与状态源唯一化（修 N5/N6）
- 启动时校验 `MIGRATION_PARALLEL_TABLE_WORKERS ≤ 池上限`（或池上限 = max(池上限, workers+2)）；
- 续传判定只读 `view_progress.completed_tables`，日志正则仅作旧任务兼容。

### 6.4 实施优先级建议
P0-6 / P0-7 直接影响数据正确性（UPDATE 漂移、LOB 静默丢失），应与第一轮 P0 同批修复；P0-8 是把已有代码接上，成本最低收益大；P1-6/P1-7 随增量同步迭代；P2-6 顺手修。
