# v2.4 部署加固与 SQL 标识符安全加固说明

> 本批次为 v2.4 第二批修复,聚焦 P1 部署配置与 SQL 注入防护,共 9 项问题。
> 第一批(P0 安全漏洞+数据正确性+稳定性 15 项)见 [v2.4安全与正确性修复说明](v2.4安全与正确性修复说明.md)。

## 一、Docker 与部署配置修复(P1-A ~ P1-C)

### 1.1 Docker Compose 高危生产配置(P1-A)
**文件**: [docker-compose.yml](../docker-compose.yml)、[Dockerfile](../Dockerfile)

**问题**:
- web 服务用 `python manage.py runserver` 作为生产命令(Django 官方明确禁止 runserver 用于生产)
- 未设置 `DJANGO_ENV=prod`,导致生产容器仍按开发模式运行(DEBUG=true、CORS 全放行、SQLite)
- Redis 无密码、暴露 6379 到宿主机所有网卡
- 无 healthcheck、无 restart 策略,容器异常不会自动恢复

**修复**:
1. `web` 改用 `gunicorn` 启动,前置 `migrate` + `collectstatic`,并显式注入 `DJANGO_ENV: prod`、`DJANGO_DEBUG: "false"`
2. Redis 改为 `expose`(仅在 compose 网络内可达)+ `--requirepass` 密码 + healthcheck
3. `celery-worker`/`celery-beat` 同步加 `DJANGO_ENV: prod`、`restart: unless-stopped`,并 `depends_on: redis: condition: service_healthy`
4. 所有服务增加 healthcheck 与 restart 策略

### 1.2 requirements.txt 缺 gunicorn + 依赖版本未锁定(P1-B)
**文件**: [requirements.txt](../requirements.txt)

**问题**: 生产镜像需要 gunicorn 但未声明;所有依赖仅有包名无版本约束,任意小版本升级可能引入破坏性变更。

**修复**: 全部依赖加版本上界约束(如 `django>=6.0,<6.1`),新增 `gunicorn>=22.0,<24.0`。

### 1.3 新增 .dockerignore(P1-C)
**文件**: [.dockerignore](../.dockerignore)

**问题**: `COPY . .` 会将 `.venv`/`.git`/`.env`/`db.sqlite3`/`logs`/`node_modules` 全部打入镜像,体积膨胀且可能泄露 secrets。

**修复**: 新增 `.dockerignore`,排除开发产物与敏感文件。

## 二、连接池失效信号(P1-D)

**文件**: [connection_pool.py:265-296](../migration_app/connection_pool.py#L265)、[models.py:17-28, 58-68](../migration_app/models.py#L17)

**问题**: `OracleConnection.save()` / `PostgresConnection.save()` 修改密码或主机后,旧连接池仍驻留内存,后续请求继续复用旧配置,导致"改了密码连不上"或"连错主机"的怪异故障,只能重启进程才生效。

**修复**:
1. `connection_pool.py` 新增 `invalidate_oracle_pool(connection_id)` 与 `invalidate_postgres_pool(connection_id, database=None)`,按 connection_id 精准失效单个池
2. `OracleConnection.save()` / `PostgresConnection.save()` 在 `super().save()` 后调用对应失效函数,触发下次获取连接时用新配置重建池
3. 失效失败被 `try/except` 包裹,不阻塞保存(下次重启时池会自然重建)

## 三、settings.py 配置加固(P1-E ~ P1-H)

### 3.1 硬编码开发者本地路径(P1-E)
**文件**: [settings.py:36-43](../oracle2polardb_pg/settings.py#L36)

**问题**:
```python
_ORACLE_CLIENT_LIB = os.environ.get(
    'ORACLE_CLIENT_LIB',
    r'/Users/xiaohaige/Downloads/instantclient_23_3',  # 开发者本机路径
)
```
进入仓库后其他环境无法使用,且暴露开发者用户名。

**修复**: 默认值改为空字符串 `''`,需用时通过 `ORACLE_CLIENT_LIB` 环境变量显式提供。

### 3.2 CORS 开发/生产逻辑冗余(P1-F)
**文件**: [settings.py:353-365](../oracle2polardb_pg/settings.py#L353)

**问题**: 开发分支同时设置白名单与 `CORS_ALLOW_ALL_ORIGINS=True`,而 django-cors-headers 在 `ALLOW_ALL=True` 时直接忽略白名单,两者共存无意义且易误导。同时 `CORS_ALLOW_CREDENTIALS=True` 与 `CORS_ALLOW_ALL_ORIGINS=True` 同时启用违反 CORS 规范(浏览器会拒绝带凭证的通配响应)。

**修复**:
- 开发环境:`CORS_ALLOWED_ORIGINS=[]`、`CORS_ALLOW_ALL_ORIGINS=True`、`CORS_ALLOW_CREDENTIALS=False`
- 生产环境:`CORS_ALLOW_ALL_ORIGINS=False`、白名单从环境变量读取、`CORS_ALLOW_CREDENTIALS=True`

### 3.3 .env.example 暴露开发者路径(P1-G)
**文件**: [.env.example:22-23](../.env.example#L22)

**问题**: `ORACLE_CLIENT_LIB=/Users/xiaohaige/Downloads/instantclient_23_3` 直接写死开发者路径。

**修复**: 改为注释的示例值 `# ORACLE_CLIENT_LIB=/opt/oracle/instantclient_23_3`。

### 3.4 PostgreSQL 元数据库未启用持久连接(P1-H)
**文件**: [settings.py:174-192](../oracle2polardb_pg/settings.py#L174)

**问题**: 通过 `DATABASE_URL` 切到 PostgreSQL 时,未设置 `CONN_MAX_AGE` 与 `CONN_HEALTH_CHECKS`,每个请求新建 TCP 连接,高并发下连接数飙升、握手开销显著。

**修复**:
```python
if 'postgresql' in DATABASES['default'].get('ENGINE', ''):
    DATABASES['default'].setdefault('CONN_MAX_AGE', int(os.environ.get('DB_CONN_MAX_AGE', '60')))
    DATABASES['default'].setdefault('CONN_HEALTH_CHECKS', True)
```
`CONN_MAX_AGE` 默认 60 秒(可经 `DB_CONN_MAX_AGE` 覆盖),复用前 ping 一次避免拿到被对端断开的失效连接。

## 四、SQL 标识符拼接安全加固(P1-I)

### 4.1 统一安全函数入口
**文件**: [pg_identifiers.py:40-65](../migration_app/pg_identifiers.py#L40)

**问题**: 项目中存在 4 处重复实现的安全函数(`_safe_oracle_identifier` in views.py、`_safe_oracle_ident`/`_quote_pg_ident` in incremental_sync.py),逻辑相同但分散,易出现行为漂移。

**修复**: 在 `pg_identifiers.py` 统一收口:
- `safe_oracle_identifier(name)`:Oracle 未加引号标识符强校验(仅放行 `[A-Z][A-Z0-9_]*`),返回大写形式
- `safe_pg_schema_name(name)`:用于 `SET search_path` 等无法绑参的语句,仅放行 `[A-Za-z_][A-Za-z0-9_]*`
- `quote_identifier(name)`:PostgreSQL/SQLite 双引号转义(已存在)
- `build_qualified_table_name(schema, table)`:`"schema"."table"`(已存在)

`views.py` / `incremental_sync.py` 删除本地副本,改为从 `pg_identifiers` 导入(`views.py` 保留 `_safe_oracle_identifier` 作为别名以避免大量调用点改动)。

### 4.2 修复 views.py 高危拼接(11 处)

| 位置 | 原拼接 | 修复方式 |
|------|--------|----------|
| `views.py:489-493` | `SET search_path TO {target_schema}, public` | `quote_identifier(safe_pg_schema_name(target_schema))` |
| `views.py:846-856` | `DROP/TRUNCATE TABLE {target_schema}.{table_name}` | `build_qualified_table_name(target_schema, table_name)` |
| `views.py:983-1024` | `SELECT COUNT(*)/SELECT * FROM {source_schema}.{table_name}` | `safe_oracle_identifier(schema).safe_oracle_identifier(table)` |
| `views.py:1188-1194` | `SELECT MAX(...) FROM {task.source_schema}.{oracle_table_name}` | `safe_oracle_identifier` 包装 schema/table |
| `views.py:1959-1967` | `CREATE SCHEMA IF NOT EXISTS "{target_schema}"`(未转义内部 `"`) | `quote_identifier(target_schema)` |
| `views.py:2009-2024` | `DROP/CREATE SEQUENCE {target_schema}.{seq_ident}` | `build_qualified_table_name(target_schema, seq_ident)` |

### 4.3 修复 view_materialization.py 高危拼接(3 处)
**文件**: [view_materialization.py:225-248](../migration_app/view_materialization.py#L225)

视图物化入口的 `SELECT COUNT(*)/SELECT * FROM {source_schema}.{view_name}` 全部改用 `safe_oracle_identifier` 包装。

### 4.4 修复 migration_validation.py 高危拼接(整个文件)

**文件**: [migration_validation.py](../migration_app/migration_validation.py)

问题最密集的模块。`count_oracle_rows`、`validate_aggregates`、`validate_row_hashes`、`validate_sample_rows` 四个函数全部改造:
- 顶部统一 `from .pg_identifiers import build_qualified_table_name, quote_identifier, safe_oracle_identifier`,删除 3 处函数内局部 import
- Oracle 端 schema/source_object/primary_key/column 全部经 `safe_oracle_identifier` 包装
- PG 端 column 全部经 `quote_identifier` 包装
- `sample_count` 转为 `int()` 防数值注入

### 4.5 修复 dashboard.py SQLite 模块高危拼接(7 处)
**文件**: [dashboard.py:1290-1342](../migration_app/dashboard.py#L1290)

SQLite 的双引号转义规则与 PostgreSQL 一致,复用 `quote_identifier`:
- `object_name` 全部经 `quote_identifier(object_name)` 包装(CREATE/DROP/DELETE/INSERT)
- 列名 `column_name`/`col` 全部经 `quote_identifier` 包装
- Oracle 端 `SELECT * FROM {task.source_schema}.{object_name}` 经 `safe_oracle_identifier` 包装

### 4.6 修复 incremental_sync.py 重复实现
**文件**: [incremental_sync.py:14-15](../migration_app/incremental_sync.py#L14)

删除本地 `_safe_oracle_ident`/`_quote_pg_ident` 重复定义,改为从 `pg_identifiers` 导入别名。原有 21 处调用无需修改。

## 六、后续建议与待优化项

### 6.1 短期(建议本批次后跟进)
1. **schema_converter.py 的 COMMENT 语句参数化**:目前用 `replace("'", "''")` 转义注释内容,功能安全但模式脆弱,建议改为 `COMMENT ON TABLE ... IS %s` 参数绑定
2. **`MigrationTaskSerializer` 入库前正则校验**:在 DRF 序列化器层对 `source_schema`/`target_schema`/`source_object`/`watermark_column`/`target_object` 加 `RegexValidator(r'^[A-Za-z_][A-Za-z0-9_]*$')`,在入口处拦截非法标识符,而非依赖每个 SQL 拼接点
3. **CI 引入 bandit 静态扫描**:检测 `cursor.execute(f"...{...}...")` 模式,防止新增未保护拼接

### 6.2 中期(架构性优化)
4. **集中式 SQL 构建层**:新增 `sql_builder.py`,封装 `build_select_count_sql(schema, table)`、`build_drop_table_sql(schema, table)` 等,所有 SQL 构建集中管理,杜绝散落拼接
5. **Oracle 端统一使用绑定变量**:部分 `SELECT *` 未用 `:bind` 变量,既影响性能(硬解析)也不利于安全
6. **`full_database.py` 的系统用户占位符改用绑定参数**:`_ORACLE_SYSTEM_USERS` 虽是硬编码常量实际安全,但模式易被复制误用

### 6.3 缺少的功能
7. **连接密码轮换审计**:`invalidate_oracle_pool`/`invalidate_postgres_pool` 触发时应写 AuditLog,记录"谁在何时改了哪个连接的密码",便于事后追溯
8. **Docker 镜像版本标签**:当前 `docker-compose.yml` 用 `build: .` 构建,建议在 CI 中产出带 git commit sha 的镜像标签,便于回滚
9. **`SECURE_PROXY_SSL_HEADER` 仅在反向代理后启用**:当前生产环境无条件启用,若直接暴露 gunicorn 会引入 X-Forwarded-Proto 伪造风险(建议增加 `USE_X_FORWARDED_HOST` 配套校验)
