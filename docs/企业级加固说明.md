# 企业级加固说明（v2.2）

> 本文档详细说明 v2.2 版本引入的安全加固、运维命令、数据类型补全、索引告警、注释迁移与多层校验体系，供运维与开发人员部署、配置与排错时参考。

## 一、安全加固

### 1.1 环境隔离（DJANGO_ENV）

通过 `DJANGO_ENV` 环境变量区分开发与生产环境，所有安全相关配置都基于此变量分支：

| 环境 | `DJANGO_ENV` | DEBUG | CORS | ALLOWED_HOSTS | SQLite |
|------|--------------|-------|------|---------------|--------|
| 开发 | `dev`（默认） | `true` | 允许所有 | `*` | 允许 |
| 生产 | `prod` | `false` | 白名单 | 必填 | 不建议 |

核心判定逻辑位于 [settings.py](../oracle2polardb_pg/settings.py)：

```python
DJANGO_ENV = os.environ.get('DJANGO_ENV', 'dev').lower()
IS_DEV = DJANGO_ENV != 'prod'
IS_PROD = DJANGO_ENV == 'prod'
```

### 1.2 SECRET_KEY 管理

- **开发环境**：使用内置的 `django-insecure-...` 占位密钥
- **生产环境**：必须通过 `DJANGO_SECRET_KEY` 环境变量提供，未设置时启动直接报错

```python
SECRET_KEY = os.environ.get('DJANGO_SECRET_KEY', '' if IS_PROD else 'django-insecure-...')
if IS_PROD and not SECRET_KEY:
    raise RuntimeError('生产环境必须通过 DJANGO_SECRET_KEY 环境变量提供密钥')
```

### 1.3 DEBUG 与 ALLOWED_HOSTS

- 生产环境强制 `DEBUG=False`
- 生产环境 `ALLOWED_HOSTS` 必须显式配置，未配置时启动报错

### 1.4 HTTPS / HSTS / Cookie 安全

仅当 `DEBUG=False` 时启用，避免开发环境 HTTPS 重定向导致访问异常：

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `SECURE_SSL_REDIRECT` | `true` | HTTP 自动跳转 HTTPS |
| `SECURE_HSTS_SECONDS` | `31536000`（1 年） | HSTS 有效期 |
| `SECURE_HSTS_INCLUDE_SUBDOMAINS` | `True` | 覆盖子域 |
| `SECURE_HSTS_PRELOAD` | `True` | 加入浏览器预加载列表 |
| `SECURE_CONTENT_TYPE_NOSNIFF` | `True` | 防 MIME 嗅探 |
| `SESSION_COOKIE_SECURE` | `True` | Cookie 仅 HTTPS |
| `CSRF_COOKIE_SECURE` | `True` | CSRF Cookie 仅 HTTPS |
| `X_FRAME_OPTIONS` | `DENY` | 禁止被 iframe 嵌入（防点击劫持） |

### 1.5 CORS 白名单

- **开发**：允许所有来源（`CORS_ALLOW_ALL_ORIGINS=True`），并预置 `localhost:5173/3000`
- **生产**：必须通过 `CORS_ALLOWED_ORIGINS` 环境变量配置逗号分隔的白名单

```bash
# 生产示例
CORS_ALLOWED_ORIGINS=https://mg.example.com,https://admin.example.com
```

### 1.6 JWT SIGNING_KEY 独立

JWT 签名密钥独立于 `SECRET_KEY`，避免一处泄漏殃及全局：

```python
'SIGNING_KEY': os.environ.get('JWT_SIGNING_KEY', SECRET_KEY),
```

可通过 `JWT_SIGNING_KEY` 环境变量单独配置。Access Token 有效期 2 小时，Refresh Token 7 天，且启用轮换 + 黑名单。

### 1.7 DRF 限流

防止暴力破解与恶意刷接口，配置位于 `REST_FRAMEWORK['DEFAULT_THROTTLE_RATES']`：

| 限流维度 | 速率 | 适用 |
|----------|------|------|
| `anon` | `60/min` | 匿名用户全局 |
| `user` | `300/min` | 认证用户全局 |
| `login` | `5/min` | 登录接口（`ScopedRateThrottle`） |

登录接口 [api.py](../migration_app/api.py) 的 `LoginAPIView` 已加 `throttle_scope='login'`，单 IP 每分钟最多 5 次登录尝试。

### 1.8 文件浏览沙箱

`BrowseDirectoriesAPIView` 原先可遍历任意目录，现改为白名单沙箱：

- 开发环境：默认允许项目根目录
- 生产环境：必须通过 `BROWSE_DIRECTORIES_WHITELIST` 环境变量配置（逗号分隔），未配置则禁用接口

使用 `Path.is_relative_to()` 校验，防止 `../` 目录穿越：

```python
allowed_roots = [Path(p).resolve() for p in whitelist]
if not any(target == r or target.is_relative_to(r) for r in allowed_roots):
    return Response({'status': 'error', 'message': '访问被拒绝：目标路径不在允许的目录范围内'}, status=403)
```

### 1.9 错误信息脱敏

新增 `_safe_error()` 统一错误响应函数，避免直接返回 `str(e)` 泄露内部异常堆栈：

- **开发环境**：返回完整错误信息便于调试
- **生产环境**：仅返回通用提示（如"操作失败"），异常详情写入后端日志

```python
def _safe_error(e: Exception, prefix: str = '操作失败') -> Response:
    logger.error('%s: %s', prefix, e, exc_info=True)
    if getattr(settings, 'DEBUG', False):
        msg = f'{prefix}: {e}'
    else:
        msg = prefix
    return Response({'status': 'error', 'message': msg}, status=status.HTTP_400_BAD_REQUEST)
```

### 1.10 GZip 压缩

新增 `GZipMiddleware`，减少 HTTP 响应传输体积，提升前端加载速度。

## 二、健康检查端点

新增两个健康检查端点，用于负载均衡器与 K8s 探针配置，位于 [urls.py](../oracle2polardb_pg/urls.py)：

| 端点 | 用途 | 检查项 | 返回 |
|------|------|--------|------|
| `GET /healthz` | 存活探针（Liveness） | 无（只要进程在就返回 200） | `{"status": "ok"}` |
| `GET /readyz` | 就绪探针（Readiness） | 数据库连通性 | 200 `{"status":"ready"}` / 503 `{"status":"not_ready"}` |

**K8s 探针配置示例**：

```yaml
livenessProbe:
  httpGet:
    path: /healthz
    port: 8000
  initialDelaySeconds: 10
  periodSeconds: 30
readinessProbe:
  httpGet:
    path: /readyz
    port: 8000
  initialDelaySeconds: 15
  periodSeconds: 10
```

## 三、Management Commands

新增 4 个运维命令，位于 [migration_app/management/commands/](../migration_app/management/commands/)：

### 3.1 init_admin —— 初始化/重置超级管理员

```bash
# 通过参数
python manage.py init_admin --username admin --password 'StrongP@ss' --email admin@example.com

# 通过环境变量（推荐，避免密码出现在命令历史）
export ADMIN_USERNAME=admin
export ADMIN_PASSWORD='StrongP@ss'
export ADMIN_EMAIL=admin@example.com
python manage.py init_admin

# 账户已存在时不重置密码
python manage.py init_admin --no-reset
```

行为：
- 账户不存在 → 创建超级管理员
- 账户已存在 → 重置密码、邮箱，并确保 `is_staff=True`、`is_superuser=True`（除非 `--no-reset`）

### 3.2 cleanup_logs —— 清理过期任务日志

```bash
# 清理 30 天前的日志（默认）
python manage.py cleanup_logs

# 清理 90 天前
python manage.py cleanup_logs --days 90

# 只统计不删除
python manage.py cleanup_logs --dry-run
```

清理 `MigrationTaskLog` 表中 `created_at` 早于 cutoff 的记录，释放存储空间。建议配合 crontab 定时执行：

```bash
# 每天凌晨 3 点清理 30 天前日志
0 3 * * * cd /opt/oracle2polardb_pg && python manage.py cleanup_logs --days 30 >> /var/log/migration_cleanup.log 2>&1
```

### 3.3 reconcile_running —— 重置孤儿任务

服务异常退出后，状态为 `running` 的任务会遗留。本命令将它们标记为 `aborted`，便于用户重新运行或继续迁移：

```bash
# 先预览（推荐）
python manage.py reconcile_running --dry-run

# 实际执行
python manage.py reconcile_running
```

建议在服务启动脚本中加入：

```bash
# 服务启动前先清理孤儿任务
python manage.py reconcile_running
```

### 3.4 healthcheck —— 命令行健康检查

用于 K8s sidecar 或脚本探针，检查项：

1. 数据库连通性
2. Redis 连通性（若配置了 `CELERY_BROKER_URL`）
3. 待处理任务数统计

```bash
python manage.py healthcheck
# 退出码 0 = 健康，1 = 不健康
```

## 六、数据类型补全（17 → 24 种）

[views.py](../migration_app/views.py) 的 `convert_oracle_to_pg_type` 函数新增 7 种 Oracle 数据类型映射：

| Oracle 类型 | PostgreSQL 类型 | 说明 |
|-------------|------------------|------|
| `XMLTYPE` | `XML` | PG 原生支持 XML（需启用 xml 模块） |
| `ROWID` | `CHAR(18)` | Oracle 物理行标识，PG 无对应，用定长 CHAR 保留 |
| `UROWID` | `CHAR(40)` | 通用行标识 |
| `BFILE` | `TEXT` | Oracle 外部文件指针，PG 无对应，用 TEXT 记录路径 |
| `INTERVAL YEAR TO MONTH` | `INTERVAL` | PG 原生支持 INTERVAL |
| `INTERVAL DAY TO SECOND` | `INTERVAL` | PG 原生支持，保留秒精度 |
| `BOOLEAN` | `BOOLEAN` | Oracle PL/SQL 布尔类型兼容 |

### INTERVAL 正则解析

支持带精度的 INTERVAL 类型，如 `INTERVAL YEAR(2) TO MONTH`、`INTERVAL DAY(2) TO SECOND(6)`：

```python
# YEAR TO MONTH
m = re.match(r'INTERVAL\s+YEAR\s*(?:\((\d+)\))?\s*TO\s*MONTH', oracle_type)
if m: return "INTERVAL YEAR TO MONTH"

# DAY TO SECOND（保留秒精度）
m = re.match(r'INTERVAL\s+DAY\s*(?:\((\d+)\))?\s*TO\s*SECOND\s*(?:\((\d+)\))?', oracle_type)
if m:
    second_precision = m.group(2)
    if second_precision: return f"INTERVAL DAY TO SECOND({second_precision})"
    return "INTERVAL DAY TO SECOND"
```

## 七、索引告警

[schema_converter.py](../migration_app/schema_converter.py) 新增 `fetch_unsupported_indexes` 函数，查询 `ALL_IND_EXPRESSIONS` 统计不被自动迁移的索引类型，并在迁移日志中告警。

### 自动迁移的索引

仅迁移 `INDEX_TYPE = 'NORMAL'` 且非约束自动创建的索引（B-tree）。

### 告警的索引类型与 PG 建议

| Oracle 索引类型 | PG 对应策略 | 说明 |
|-----------------|-------------|------|
| FUNCTION-BASED NORMAL | 表达式索引 | `CREATE INDEX ... ON ... (表达式)` |
| BITMAP | GIN 或普通 B-tree | PG 无原生位图索引 |
| REVERSE | 普通 B-tree | PG 无反向键索引 |
| DOMAIN / CLUSTER | 人工处理 | PG 无对应 |

告警示例日志：

```
[WARN] 表 EMPLOYEES 有 2 个索引未自动迁移（需人工补建）：
  - IDX_EMP_UPPER_NAME (FUNCTION-BASED NORMAL): 表达式 UPPER("ENAME")
    建议：在 PG 上创建表达式索引 CREATE INDEX ... ON ... (UPPER("ENAME"))
  - IDX_EMP_BMP_DEPT (BITMAP): 列 DEPTNO
    建议：PG 无位图索引，转 GIN 或普通 B-tree 索引
```

## 八、表/列注释迁移

[schema_converter.py](../migration_app/schema_converter.py) 新增 `apply_table_comments` 函数，将 Oracle 表/列注释迁移到 PolarDB-PG。

### 数据来源

- 表注释：`ALL_TAB_COMMENTS.COMMENTS`
- 列注释：`ALL_COL_COMMENTS.COMMENTS`

### 目标 DDL

```sql
COMMENT ON TABLE schema."table" IS '注释内容';
COMMENT ON COLUMN schema."table"."column" IS '注释内容';
```

### 执行顺序

注释迁移在 `apply_post_table_schema` 中最后执行（默认值 → 约束 → 索引 → 注释），失败不影响主流程，仅记 `[WARN]` 日志。

> 注释中的单引号会自动转义为 `''`。

## 九、多层数据校验体系

[migration_validation.py](../migration_app/migration_validation.py) 从仅行数校验升级为 4 层校验体系：

| 层级 | 函数 | 校验方式 | 能发现的问题 | 性能 |
|------|------|----------|-------------|------|
| 1. 行数 | `validate_row_counts` | `COUNT(*)` 对比 | 行数不一致 | 低（最快） |
| 2. 聚合 | `validate_aggregates` | SUM/COUNT/MIN/MAX 对比 | 批量数据错误（如 UPDATE 改值未变行数） | 中 |
| 3. 哈希 | `validate_row_hashes` | 按主键分批 MD5 对比 | 精确定位差异行 | 高（大表慢） |
| 4. 抽样 | `validate_sample_rows` | DBMS_RANDOM 随机抽 N 行逐行对比 | 大表快速验证 | 低 |

### 9.1 行数校验（validate_row_counts）

最低保障，行数相等 ≠ 数据一致。返回 `(是否一致, 源行数, 目标行数)`。

### 9.2 聚合校验（validate_aggregates）

对每个数值列（NUMBER/FLOAT/BINARY_FLOAT/BINARY_DOUBLE）对比 SUM/COUNT/MIN/MAX，浮点数容差 0.01。能捕获批量数据错误（如 UPDATE 把 A 改成 B，行数不变但 SUM 变化）。

### 9.3 哈希校验（validate_row_hashes）

按主键分批（默认 1000 行/批，最多 100 批）计算行 MD5 对比，精确定位差异行：

- **Oracle 端**：`NVL(TO_CHAR(col), '') || '|' || ...` → `MD5()`
- **PG 端**：`COALESCE(col::text, '') || '|' || ...` → `MD5()`
- 按主键排序分批 `OFFSET ... FETCH NEXT ... ROWS ONLY`
- 找到前 5 个差异后停止全表扫描

返回 `(是否一致, 校验行数, 差异行数)`。

### 9.4 抽样校验（validate_sample_rows）

通过 `DBMS_RANDOM.VALUE` 随机抽取 N 个主键（默认 100），逐行逐列对比，数值容差 0.01。适用于大表快速验证。

返回 `(是否一致, 抽样行数, 差异行数)`。

### 9.5 综合校验（validate_full）

`validate_full` 函数按顺序执行上述 4 层校验，汇总结果。**校验失败默认不阻塞迁移**，仅记 `[WARN]` 日志；可通过 `strict=True` 强制阻塞。

### 11.2 生成密钥

```bash
# DJANGO_SECRET_KEY
python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"

# JWT_SIGNING_KEY
python -c "import secrets; print(secrets.token_urlsafe(50))"

# MIGRATION_FERNET_KEY
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

python manage.py init_admin

# 5. 健康检查

## 十三、审计日志与 RBAC 权限控制（v2.3 新增）

### 13.1 审计日志模型（AuditLog）

新增 `AuditLog` 模型，记录用户关键操作的审计轨迹，表结构如下：

| 字段 | 类型 | 说明 |
|------|------|------|
| `user` | ForeignKey | 操作用户（删除时置 NULL） |
| `action` | CharField(50) | 操作类型（如 `start_task`、`delete_task`、`create_connection`） |
| `target_type` | CharField(50) | 目标类型（如 `task`、`connection`、`settings`） |
| `target_id` | IntegerField | 目标对象 ID |

### 13.2 RBAC 三级角色模型

新增 `UserProfile` 模型，与 Django User 一对一关联，支持三级角色：

| 角色 | 权限范围 | 对应 Django 字段 |
|------|---------|-----------------|
| `admin`（管理员） | 所有操作 + 系统设置 + 创建数据库/用户 | `is_staff=True` 或 `profile.role='admin'` |
| `operator`（操作员） | 创建/编辑/删除连接、启动/取消/删除任务 | `profile.role='operator'` |
| `viewer`（只读用户） | 仅查看任务列表、连接列表、日志等 | `profile.role='viewer'` |

### 13.3 DRF 权限类（permissions.py）

新增三个权限类，用于 DRF ViewSet/APIView：

| 权限类 | 适用操作 | 检查逻辑 |
|--------|---------|---------|
| `IsAdmin` | 系统设置、创建数据库/用户/表空间 | `request.user.is_staff == True` |

| `IsViewerOrAbove` | 查看任务列表、连接列表等只读操作 | 仅需登录 |

## 十四、后续优化建议

### 14.1 审计日志优化

- **定时清理**：建议添加 `cleanup_audit_logs` management command，定期清理超过 90 天的审计日志
- **异步写入**：高并发场景可将审计日志写入改为异步（Celery task），避免阻塞主请求
- **分表存储**：按月份或季度分表，避免单表数据量过大

### 14.2 RBAC 权限优化

- **前端联动**：前端应根据用户角色隐藏/禁用高危按钮（如普通用户不显示"删除任务"）
- **角色初始化**：`init_admin` 命令自动为管理员创建 `UserProfile` 并设置 `role='admin'`
- **权限缓存**：高频权限检查可缓存用户角色，减少数据库查询

### 14.3 安全加固补充

- **操作二次确认**：高危操作（删除任务、删除连接）建议添加前端二次确认弹窗
- **敏感字段脱敏**：审计日志 payload 中避免记录密码等敏感信息
- **登录审计**：登录成功/失败也建议记录到 AuditLog，便于安全审计
